# ADR-0010: 技術債與改善建議分級歸檔架構

- **狀態**：`ACCEPTED`
- **日期**：2026-08-21
- **相關規格**：[SPEC-0010: 技術債與架構改善意見追蹤管理系統](../specs/0010-technical-debt-tracking-system.md)

---

## 1. 決策背景 (Context)

在專案敏捷開發與代碼審查過程（如 PR #83）中，審查常提出有助於系統長期可維護性的建議（如 DRY 重構、效能微調）。
若未加記錄，容易在後續迭代中被遺忘；若在當期強行實作，則可能違反 KISS 原則與造成過度工程化。
使用者明確要求在 `docs/` 目錄下建立一個統一存放技術債與架構改善建議的專屬目錄。

---

## 2. 架構決策 (Decision)

1. **目錄與命名結構**：
   - 建立 `docs/debts/` 作為技術債集中管理空間。
   - 文件採用 4 位數字編號 `0001-<name>.md`，並以 `docs/debts/README.md` 作為動態索引看板。
2. **生命週期與收錄守則**：
   - **僅收錄「未即時執行之改善建議」**：當期已修復者不建檔；歷史技術債若在未來 PR 中修復，將其狀態更新為 `RESOLVED`。
   - **標準四段式文檔模板**：包含【背景與代碼現狀】、【問題分析與暫緩理由】、【建議重構方案】與【觸發處理時機】。
3. **Agent 工作流防護閉環**：
   - 於 `AGENTS.md` 規範 Agent 在 `/code-review` 與 `/handoff` 階段自動檢查並落實未完成建議之歸檔。

---

## 3. 影響與效益 (Consequences)

### 正面效益
- 建立清晰可查閱的架構演進待辦清單，杜絕技術債遺忘。
- 防止 PR 範圍蔓延，兼顧當期敏捷交付與長期架構演進。

### 潛在權衡 (Trade-offs)
- 每次 Code Review 結束後需額外維護技術債文檔與索引，需依靠規範嚴格執行。
