# 0106. 肌肉書僮真實日 K 受控並發增量回補與本地持久化加速架構 (Muscle Booker Incremental Backfill & Local Cache)

- **狀態**：ACCEPTED
- **日期**：2026-09-09
- **議題**：徹底解決肌肉書僮雷達在非自訂清單（如台股市值 50、美股巨頭 50 等目標池）長時間停滯在「🟡 回補中...」的觸發漏失 BUG，建立合法高效的短期增量日 K 拉取機制、受控並行隊列、以及頂部本地快取同步狀態條。

---

## 背景與問題陳述 (Context & Problem Statement)

使用者在切換至「台股市值 50（TW50）」或其他目標池時，畫面所有標的（如 2330 台積電、2454 聯發科、2317 鴻海等）長時間卡在「🟡 回補中...」且箱體位階顯示「資料未就緒」。

經深度剖析，存在以下架構缺陷：
1. **觸發漏失 (Missing Trigger Bug)**：
   `MuscleBookerWorkspace.tsx` 的背景回補邏輯硬編碼了 `if (missing.length > 0 && selectedPool === 'CUSTOM_WATCHLIST')`。當目標池為台股 50、美股 50 或在庫持股時，若 IndexedDB 尚未存有該 50 檔日 K，系統雖然收集了缺損標的清單，卻**未發出任何網路請求**，導致畫面永久停留在「回補中...」。
2. **全量請求過重且易受風控限制 (Overweight Full-History Query)**：
   原 `historicalOhlcvBackfill.ts` 每次請求均硬編碼 `period1=0`，拉取該標的數十年全量歷史。50 檔標的全量傳輸數據龐大，極易觸發遠端（Yahoo Finance）的 429 Too Many Requests 阻擋。
3. **缺乏增量補齊機制與進度透明度**：
   肌肉書僮指標僅需近 60~120 根日 K。若本地已具備歷史，僅需向遠端請求自「最後收盤日 - 7 天」至今的最新日 K 補齊即可，且需提供透明的同步進度反饋。

---

## 決策方案 (Decision)

我們依據事實為本與第一性原理，實施以下核心加速與本地化架構：

1. **短期增量區間請求 (`calculateIncrementalPeriod1`)**：
   - **本地已存在日 K**：以最後一根 K 線日期往前倒推 7 天為 `period1`，向遠端僅請求最近數天數據（僅數百 bytes），傳輸時間壓至 150~200ms。
   - **本地無日 K**：請求最近 180 天（約 6 個月，~120 根日 K），足以計算 MA60 與 Darvas 箱體，傳輸量減幅超過 90%。
   - 透過 `mergeDailyCandles` 自動與本地既有 K 線去重合併，並寫入 IndexedDB（`saveSymbolOhlcv`）。
2. **全目標池受控並行回補隊列 (Controlled Concurrency Queue)**：
   - 移除 `selectedPool === 'CUSTOM_WATCHLIST'` 限制，所有目標池（TW50、US50、在籍持股、自訂清單）均享有一致的自動增量回補。
   - 採用 Concurrency = 3 的受控並發隊列，標的之間節流 60ms，兼顧極速加載與防止 API 濫用。
   - 每完成一檔即時寫入 `cachedCandlesMap`，畫面一檔接一檔即時解鎖技術指標，實現流水般流暢體驗。
3. **頂部本地日 K 快取狀態與增量同步工具列**：
   - 即時顯示：`本地日 K 快取就緒度：X / Y 檔 (Z%)`。
   - 同步進行時：展示動態平滑進度條與「⏳ 正在增量同步：2330 (12/50)...」。
   - 全數就緒時：顯示「🟢 本地日 K 均已就緒 (支援離線即時秒算)」。
   - 提供「🔄 增量同步最新收盤」按鈕，讓投資人在盤後可一鍵手動補齊當日最新收盤價。

---

## 結果與影響 (Consequences)

### 正向影響 (Positive)
- **徹底修復回補停滯**：台股 50、美股 50 等任何目標池均能自動受控並發回補，不再永久卡在「回補中...」。
- **傳輸量減少 90%+**：增量請求大幅縮短下載時間，避免遠端 429 速率限制。
- **真正的本地持久化**：下載過一次即存於 IndexedDB，下次進站離線即時秒開，日後僅增量補齊短期差距。
- **全專案回歸綠燈**：57 個測試套件、649 個單元測試 100% 通過，TypeScript 0 型別錯誤。
