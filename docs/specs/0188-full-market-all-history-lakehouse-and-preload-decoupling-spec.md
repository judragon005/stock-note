# 規格書 0188：全市場全歷史數據湖倉架構解耦、250日預載視窗與跨模組本地優先整合工程 (Spec 0188)

## Problem Statement

當前使用者在檢視系統數據與歷史回補時，發現了嚴重的架構混淆、資料殘缺與跨模組資料孤島現象：
1. **資料庫儲存深度與預載視窗混淆**：系統原先將「前端戰情室極速預載 250 個交易日 (Preload Window)」與「底層 SQLite 湖倉儲存深度」錯誤綁定。入庫腳本硬編碼 `limit = 260` 截斷，導致本機既有自 2016 年至今累積的十餘年真實歷史日 K 與籌碼無法全量沉澱；過期修剪器更定期執行 `DELETE` 刪除超過 260 天的日 K，破壞了資料庫作為「全歷史資產」的本質。
2. **大盤基準依賴靜態假資料 (Mock Fallback)**：美股 SPY 基準價格手動寫死至 2025 年 10 月，台股加權指數依賴靜態 JSON。明明美股與台股管線已天天採集真實大盤數據，量化模組卻未與本地 SQLite 湖倉連通，違反 Zero-Mock 原則。
3. **歷史淨值與除權息捨近求遠**：持股歷史淨值回推 (`historicalPriceFetcher`) 每次都發起脆弱的外部 Yahoo Finance 網路請求，頻繁遭遇 `ECONNRESET` 逾時與破圖；歷年股利查詢 (`dividendService`) 繞過本地 `corporate_action_calendar` 表直接撞外部 API。
4. **雙軌回補進度口徑脫鉤與看門狗熔斷遺留缺口**：雙軌回補時後端折半計算總進度（13%），前端 UI 卻直接與台股單軌天數 (63/250天) 混排，造成「數學算錯」的嚴重視覺誤解；單日看門狗 45 秒熔斷後跳過的日期缺少尾盤自動補漏，導致歷史缺口永久殘留。

## Solution

實施端到端「全市場全歷史湖倉架構解耦與跨模組本地優先管線」：
1. **儲存深度徹底解耦**：解除入庫腳本的 260 天截斷（改為全量入庫），封印修剪器的日 K 刪除指令，確立 SQLite 湖倉為「全市場全歷史 Append-Only」儲存庫。
2. **應用層嚴守 250 天預載視窗**：API 端點預設維持 `limit=250`（支援動態擴展至長天期），確保前端戰情室與圖表維持 < 10ms 秒開體驗與 MA250 年線運算。
3. **全模組落實 Lakehouse-First 本地優先**：大盤基準 (TAIEX & SPY)、歷史淨值回推、歷年除權息政策全面改為「優先讀取本地 SQLite 湖倉，查無才回退外部網路」，徹底消除連線逾時破圖與靜態假資料。
4. **回補進度視覺口徑分離與看門狗尾盤自動補漏**：前端清晰分列「全域雙軌總進度」與「單軌階段天數與百分比」；250 天回補結束時，針對熔斷失敗日期自動執行一次冷卻補漏，達成 100% 綠燈閉環。
5. **籌碼表降序索引優化**：為 `tw_institutional_chips` 補齊 `(symbol, date DESC)` 複合索引，消除歷史籌碼百萬筆數據時的排序開銷。

## User Stories

1. 作為長期投資人，我希望底層 SQLite 湖倉能完整容納本機十餘年累積的全部個股日 K 與籌碼數據，以便隨時進行跨週期宏觀比對，不再被人工砍成 260 天。
2. 作為系統使用者，我希望在背景排程或清理腳本執行時，辛苦累積的全歷史數據絕對不會被系統默默 `DELETE` 刪除。
3. 作為主力戰情室使用者，我希望在開啟戰情室時依然能享受最近 250 個交易日的秒開體驗與 MA250 年線分析，不受全歷史百萬筆資料膨脹的卡頓影響。
4. 作為技術分析者，我希望在需要觀察長線 Darvas 箱體或 3 年趨勢時，中介層 API 能支援動態擴展天數（如 `limit=750` 或 `limit=all`），隨需載入更長歷史。
5. 作為量化投資者，我希望在「量化分析」工作區查看投資組合與標普500 (SPY) 的比較時，SPY 走勢是來自 SQLite 湖倉最新真實收盤價，而不是停留在 2025 年 10 月的手填假資料。
6. 作為績效檢驗者，我希望在計算投資組合歷史淨值走勢時，系統能優先讀取本機已有的歷史日 K，不再因為 Yahoo Finance 伺服器 `ECONNRESET` 導致資產曲線破碎。
7. 作為除權息關注者，我希望在查閱歷年股利時，系統能優先從本地資料庫秒開除權息紀錄，不再受限於外部 FinMind API 的免費配額或斷線。
8. 作為回補進度觀察者，我在啟動雙軌全歷史回補時，希望介面清楚分開標示「台美總進度百分比」與「台股單軌進度百分比及天數」，不再產生算術混淆。
9. 作為自動化維運者，當政府 API 偶發卡死被 45 秒看門狗熔斷時，我希望主流程在跑完 250 天後能自動對這幾天發起一次尾盤補漏，無需我手動記錄與重新執行。
10. 作為大數據查詢者，我希望在檢索個股歷史籌碼時，資料庫已建立適當的降序複合索引，使 250 天籌碼提取在 1ms 內極速完成。

## Implementation Decisions

### 1. 本機歷史數據庫全量入庫與截斷解除 (Storage Decoupling)
- 將歷史 CSV 入庫模組之截斷參數預設由 `260` 調整為 `0`（代表無限制，全量入庫）。
- 遍歷本機歷史目錄時，將所有可用之歷史日 K 與法人籌碼完整寫入 SQLite，不進行日期切片截斷。
- 嚴格維持事務分批寫入（Chunk Size: 500~1000），避免單一大事務長時間鎖定資料庫。

### 2. 資料修剪器行為安全封印 (Pruning Neutralization)
- 移除日 K 線表 (`daily_candles`) 與籌碼表 (`tw_institutional_chips`) 的基於天數自動 `DELETE` 邏輯。
- 修剪模組僅保留：清理過期暫存檔案 (`*.tmp`, `*.temp`)、校驗資料庫完整性 (`PRAGMA integrity_check`) 與必要時的磁碟重組 (`VACUUM`)。

### 3. API 中介層動態天數與預載視窗對齊 (API Query Protocol)
- `/api/market/history/:symbol` 預設維持 `limit = 250`。
- 支援動態查詢參數 `limit`，允許傳入任意整數或 `all`（當 `query.limit === 'all'` 時不加 LIMIT 子句）。
- 確保上櫃標的雙向別名相容性維持正常。

### 4. 大盤基準與 SPY 真實數據直連 (Zero-Mock Benchmark)
- 重構大盤基準取數邏輯：當請求 SPY 或 TAIEX 基準序列時，優先調用湖倉日 K 查詢接口提取真實歷史走勢。
- 僅在本地湖倉完全查無該標的數據時，才安全降級為靜態備份常數。

### 5. 跨模組本地優先路由 (Lakehouse-First Routing)
- 歷史收盤價獲取模組在組裝請求時，先透過本機 API 檢查目標標的在指定區間的日 K 是否在庫；若已在庫則直接採用，缺漏部分才對外發起請求。
- 歷年股利服務在對外發起 HTTP 請求前，先檢索本地除權息日曆表；在庫記錄充足時直接解析回傳。

### 6. 看門狗尾盤補漏與雙軌進度口徑對齊 (Backfill Resilience & UX)
- 雙軌回補全域狀態擴充欄位：明確分離 `tw.progressPct`、`us.progressPct` 與 `globalProgressPct`。
- 前端進度卡片重構排版，明確展示雙軌階段與各自完成度。
- 日期驅動回補主循環結束時，若 `failedDates.length > 0` 且 `failedDates.length <= 5`，在延遲 5 秒冷卻後，自動對失敗日期發起一次單輪重試，成功者自失敗清單剔除並入庫。

### 7. 資料庫索引補強 (Database Index Enhancement)
- 在資料庫連線初始化層中加入：
  ```sql
  CREATE INDEX IF NOT EXISTS idx_chips_symbol_date ON tw_institutional_chips(symbol, date DESC);
  ```
- 提升 `busy_timeout` 至 15000ms，徹底杜絕 Windows 併發讀寫時的 `SQLITE_BUSY`。

## Testing Decisions

### 1. 測試品質原則
- 遵循「只在公開介面縫隙 (Test Seams) 測試外部行為，不耦合內部暫存變數」。
- 100% 覆蓋邊界案例：如全量入庫無截斷驗證、修剪器不刪除歷史日 K、API 動態 limit 回傳筆數、大盤基準優先讀取真實日 K、尾盤自動補漏觸發。

### 2. 測試縫隙 (Test Seams)
- **Seam 1: 入庫與修剪深度縫隙**
  - 驗證傳入 500 根歷史 CSV 時，入庫函數全量寫入 500 根，且修剪器執行後 500 根依然完整存在。
- **Seam 2: 中介層 API 動態 limit 查詢縫隙**
  - 驗證 `/api/market/history/2330` 預設回傳 250 筆；帶入 `?limit=400` 回傳 400 筆；帶入 `?limit=all` 回傳全部筆數。
- **Seam 3: 大盤基準 SPY 真實性縫隙**
  - 驗證當 SQLite 存在 SPY 日 K 時，基準服務產出的價格序列來自資料庫真實收盤價，而非靜態常數。
- **Seam 4: 看門狗尾盤補漏縫隙**
  - 模擬單日逾時熔斷後，驗證主循環結束時能自動觸發尾盤重試並修補缺漏。

## Out of Scope

1. 高頻分時 Tick / 分鐘 K 線入庫（湖倉維持日 K 與日級籌碼顆粒度）。
2. 重構前端 IndexedDB 私密帳本加密架構（維持既有安全機制）。
3. 商業付費金融 API 串接。
