## 1. 任務核心背景與問題根因剖析

### 1.1 為何先前「200MA 為 0.0%」？
- **根本原因 (Root Cause)**：
  1. **聯集天數稀釋**：SQLite 的 `daily_candles` 同時混存美股與台股日 K。美股在台股連假期間仍正常開市，導致全資料庫近 200 個交易日取聯集時，純台股在該 200 天視窗內實際只有 180~192 天。
  2. **硬編碼門檻剔除**：原 SQL 使用 `HAVING COUNT(DISTINCT date) >= 200`，使所有台股標的因計數不足 200 天而**全數被 HAVING 條件過濾剔除**，導致分母分子皆為 0，最終回傳 `0.0%`。
  3. **非股票代號稀釋**：台股資料庫中混入 4,660 筆 6 碼認購/認售權證（如 `03001P`），若未剔除會嚴重拉低有效均線比率。
- **修復方案**：
  - 台美兩大市場**獨立定錨**各自最新交易日與近 200 日交易日清單（`twDates` vs `usDates`）。
  - 台股透過 `GLOB '[0-9][0-9][0-9][0-9]' OR (LIKE '00%' AND LENGTH <= 6)` 嚴格過濾非 00 權證，僅保留純股票與 00 ETF。
  - 將 200MA 合格天數門檻由硬寫死 200 天調整為 `Math.min(180, availableDates.length)`。
  - 成功還原真實 200MA 年線寬度（約 25.2%）。

### 1.2 融資去槓桿減幅「-81.2%」虛假恐慌
- **根本原因**：當日台股盤後籌碼若僅同步完成部分標的（如僅收錄 364 檔而非正常的 1,900+ 檔），單日融資總餘額被腰斬，導致融資減幅瞬間暴跌至 `-81.2%`，觸發偽「去槓桿充分」信號。
- **修復方案**：在 `getMarginDeleveragingRatio` 中統計每日標的檔數，以近 60 日歷史最高檔數之 60%（或 1,000 檔）建立動態安全門檻；若最新日檔數不足，自動回溯至上一完整交易日，杜絕殘缺日假訊號。

### 1.3 移除外部目錄依賴與假數據寫死
- **外部目錄隔離**：嚴格杜絕使用本機獨有的 `D:\APP\諮詢\私人\慢富之路` 外部路徑。所有數據來源全數轉向專案內部 SQLite 資料庫，或 FRED 官方免 API Key 的公開 CSV 端點（`https://fred.stlouisfed.org/graph/fredgraph.csv?id={seriesId}`）。
- **去偽存真與誠實空狀態**：前端 Workspace 與卡片元件全量拔除寫死假數據（如硬編碼的 `51.5 / 53.8 / 1.31` 等常數），無資料或 API 異常時誠實顯示 `--`，絕不以虛構數值欺瞞使用者。
- **拒絕重複造輪子**：拔除 `zavySlowWealthEngine.ts` 原先自行拼湊的簡陋偽算術平均與降槓桿邏輯，全面委託調用專案既有經充分測試之 `rebalancingEngine.ts`（大類資產動態平衡、質押設質保護瀑布流）與 `monteCarloFireEngine.ts`（30x 本金與 Coast-FIRE 測算）。
